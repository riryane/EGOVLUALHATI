E-Tulong

"One Tap, One Tulong." — Technical Brief & Q&A Preparation Guide
Lualhatinnovators · University of the East – Manila · eGov Hackathon · Integrated module concept for the eGovPH Super App
Read this first — how to frame the prototype. The implementation choices (static HTML, a hosted PostgreSQL service, sandbox API keys in the client) were deliberate time-constraint decisions made to spend the hackathon proving what actually matters: the idea, the live eGov API orchestration, and the end-to-end process design — identity, eligibility, evidence, verification, and due process. Every one of those flows runs on real government APIs. The delivery stack is disposable; the design is the contribution.

1. What E-Tulong is

A one-stop government assistance module for the eGovPH Super App: citizens discover the ayuda they qualify for, apply once with documents they already have on record, verify identity biometrically, and track and claim benefits — while agencies review, decide with written reasons, and confirm claims securely. It consumes four existing eGov services rather than rebuilding any of them.

2. Architecture

Browser (citizen app + agency portal, same codebase)
 ├── eGov SSO ............ identity & auto-registration (hackathon-sso.e.gov.ph)
 ├── eMessage ............ SMS: OTP, status notices, claim codes (ws-message.e.gov.ph)
 ├── eGov Face Liveness .. biometric proof of presence (hackathon-face-liveness-api.e.gov.ph)
 ├── eGov AI ............. document OCR extraction (egov-ai-core-ws.oueg.info)
 └── PostgreSQL .......... users / programs / applications / id_cards
                           (Supabase for the MVP — any government-hosted Postgres in production)

Why buildless/static: zero deployment friction and it proves every integration is plain HTTP — the calls port unchanged to any production stack. Why Supabase: a stand-in for the agency-side data service; four tables of standard PostgreSQL with nothing vendor-specific.

3. The four live API integrations

3.1 eGov SSO — identity & auto-registration

  • OAuth2 authorization-code pattern: eGovPH redirects with a single-use exchange_code → POST /api/token (partner code + secret) → bearer token → POST /api/partner/sso_authentication → full citizen profile including the PhilSys record.
  • Users are matched by uniqid per the eGov integration guide: existing → profile refresh; new → auto-registration, program catalog, Digital ID.
  • The SSO payload is the source of truth for profile data — the app never edits profiles locally, satisfying the eGov checklist ("profile updates occur exclusively through eGovPH").

3.2 eMessage — the SMS channel (three uses)

  • Login OTP: 6-digit code, 5-minute expiry, account resolved by registered mobile — a possession factor.
  • Status notifications: every agency decision texts the citizen, including the written reason on rejection.
  • Claim codes: fresh code generated at the counter for two-factor pick-up (see §6).

3.3 eGov Face Liveness — anti-ghost-beneficiary

  • POST /v1/liveness/session (action post) → hosted scanner embedded inside the app frame (iframe with camera permission); completion via postMessage plus result polling.
  • GET /v1/liveness/result/{token} → we enforce the vendor threshold: SUCCEEDED and confidence ≥ 95.0; anything less is rejected with retry. Only a passing scan records the application.

3.4 eGov AI Document Extractor — OCR plus our verification layer

  • Access code → POST /api/v1/egov/integration/token → 48-hour token, 200 credits; we cache, auto-refresh before expiry, and retry once on 401.
  • Camera frame (canvas → JPEG) → multipart/form-data → structured extracted fields.
  • Our layer: OCR reads anything — it doesn't know what the program requires. Extracted text is matched against keyword sets derived from the required document's name; a mismatch raises "Wrong Document?" That's the difference between OCR and verification.

4. Data model & eligibility engine

TablePurposeKey columns
usersCitizen profiles from SSOegov_uniqid (identity binding), profile fields, consented_at (RA 10173)
assistanceProgram catalogrules (eligibility criteria), documents (checklist), requirements
applicationsOne row per applicationstatus (state machine), admin_note, citizen_note (appeal), submitted_documents (evidence snapshot), claim_code + expiry
id_cardsDigital ID render dataPhilSys PCN from SSO

Eligibility is computed, not stored. Each program carries machine-readable rules evaluated against the live profile: age range (from birth date), residency (address match), profile completeness (names exactly what's missing), and no other active benefit in the same category (prevents stacking). All rules met → Eligible; otherwise Possibly Eligible with a per-rule pass/fail checklist. The same engine runs on the agency side, so citizen and officer see one truth. Adding a program or rule is a data change, not a code change.

5. Application lifecycle — due process by construction

pending ──► approved ──► for_pickup ──► done ──► expired (cycle reset → may re-apply)
   │
   ├──► info_requested ──(citizen submits document)──► pending
   │
   └──► rejected ──(cooldown; may appeal during it)──► appealed ──► approve / final deny
  • All transitions are agency-side; citizens see read-only status — except the citizen-initiated appeal and info response.
  • Deny and Request Info require a written message, shown in-app and sent by SMS — the system will not allow a reasonless rejection.
  • Rejection triggers a re-apply cooldown (demo: 2 min; production: policy, e.g. 30 days). Appeals are allowed during the cooldown — that is the point of due process.
  • Active applications block duplicates; "expired" preserves history while unlocking next-cycle re-application.

6. Secure claiming — two-factor pick-up

  1. Something you have: at the counter the officer sends a fresh 6-digit SMS code (5-minute expiry) to the registered number; the citizen reads it back; the officer confirms against the freshest database state. Codes are single-purpose and cleared after use.
  2. Something you are: identity was bound by face liveness at application time and the Digital ID at the counter.

Result: benefits cannot be claimed by proxy — the registered SIM must be physically present.

7. Evidence trail

  • Verified documents are keyed by document name — one captured SSS record satisfies every program that needs it. This is the "stop re-submitting the same photocopy" pain point, implemented.
  • Each submission stores a snapshot of the document evidence (what was verified and how: eGov record vs. camera OCR). The agency reviews evidence as submitted, immune to later changes.

8. Privacy (RA 10173)

  • Consent gate on first use; consent timestamp stored.
  • Plain-language privacy notice: what is collected, why, legal basis, retention, the citizen's NPC rights, DPO contact.
  • Profile data flows exclusively from eGovPH; roadmap adds audit logging and retention enforcement.

10. Hard questions — model answers

Q: "Your secrets are in client-side JavaScript. That's a security hole."
"Correct — and it's a documented, deliberate MVP concession. The prototype is intentionally backend-less so we could prove all four eGov integrations within the hackathon window. Production moves every token exchange behind a backend proxy; the browser never sees a secret; all sandbox keys get rotated. It's item one in our limitations table."
Pattern for all security questions: agree → "deliberate and documented" → production design. Never defensive.
Q: "Why should I trust your eligibility results?"
"Eligibility isn't hardcoded — a rules engine computes it from the citizen's SSO profile: age, residency, profile completeness, and no other active benefit in the same category, which prevents stacking. The same engine runs on the agency side, so both parties see one computation. Production runs it server-side, since clients can't be trusted to declare themselves eligible."
Q: "How do you prevent ghost beneficiaries or claiming for someone else?"
"Three layers: identity at registration through eGov SSO bound by uniqid; identity at application through Face Liveness at their recommended threshold — SUCCEEDED, ≥95 confidence, below it we reject; and possession at claim — a fresh 6-digit SMS code with 5-minute expiry sent to the registered SIM, which must physically be at the counter. That's two-factor claiming."
Q: "OCR just reads text. How do you know it's the right document?"
"That's why we built a verification layer above the extractor: extracted text is matched against keyword sets for the required document — a driver's license photographed in place of a barangay certificate is flagged 'Wrong Document'. And submissions snapshot the evidence, so the agency reviews what was actually submitted."
Q: "What happens when eGov's APIs go down?"
"We lived that — eMessage and eGov AI both went down during development. Every path fails soft: clear error states and labeled demo fallbacks, with the real path resuming automatically when service returns. Our design rule was: never silently fake success."
Q: "Why Supabase / why plain HTML? Is this production technology?"
"Those were time-boxed delivery choices, not architectural commitments. The data layer is four tables of standard PostgreSQL that port to any government-hosted database unchanged; the frontend proves the integrations are plain HTTP. What we're presenting is the idea, the API orchestration, and the process design — the stack underneath is replaceable in a sprint."
Q: "How does this scale — more programs, more agencies, 110M citizens?"
"A new ayuda program is a database row — rules plus a document checklist — zero code changes. The heavy lifting (identity, SMS, biometrics, OCR) already runs on eGov's national infrastructure; our layer is thin orchestration. Agency onboarding is configuration, not development."
Q: "What about the Data Privacy Act?"
"Built in: consent gate with stored timestamp on first use, a plain-language privacy notice covering collection, purpose, retention, and NPC rights, and profile data flowing exclusively from eGovPH per their checklist. Roadmap adds audit logging and retention enforcement."
Q: "A citizen gets rejected. Then what?"
"The system won't allow a reasonless rejection — the officer must write one and it's SMSed to the citizen. A cooldown prevents immediate re-application, but the citizen may appeal during it; the officer sees the reason and the appeal side by side and can overturn. Due process is enforced by the state machine, not left to policy."
Q: "What's real and what's mocked?"
"All four eGov APIs are live: SSO with auto-registration, real SMS through eMessage, real face liveness through their scanner embedded in-app, real OCR with managed token lifecycle. The only non-real elements are clearly labeled demo fallbacks for sandbox downtime."
Q: "Isn't this just duplicating what agencies already have?"
"The opposite — agencies keep their systems; E-Tulong is the missing citizen-facing layer on top of infrastructure the government already built. We wrote zero identity code, zero SMS infrastructure, zero biometrics. The gap has never been the assistance — it's that no single system makes it visible, applicable, and claimable. That's the layer we built."

11. Delivery — leaving a mark in the 1-on-1

  1. Open with the live phone, not slides. Apply → a real SMS lands on the table → agency portal → approve → second SMS. A judge who receives a text message remembers the team.
  2. Volunteer a weakness first. "Before you ask — yes, secrets are client-side; here's why and here's the fix." It converts their attack list into your agenda and signals engineering maturity.
  3. One drives, one answers. Assign sections of this brief to specific teammates; rehearse the handoffs. Silence kills more Q&As than wrong answers.
  4. Tell the ecosystem story in one line: "Zero identity code, zero SMS infrastructure, zero biometrics — four government APIs consumed, one missing citizen experience shipped." That's exactly what this hackathon judges.
  5. Bridge, never bluff: "We haven't handled that — the design would be X." Judges probe for honesty as much as knowledge.
  6. Close by handing over this document. Real documentation with a limitations table is rare at hackathons; it outlives the session.
