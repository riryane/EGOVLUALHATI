2. Loopholes & workarounds — with the fix for each

Ordered by severity. Volunteer #1 before they find it.

#1 · Anyone can rewrite the database
RLS is off and the publishable key ships in page source — a person with DevTools could PATCH their own application to approved, read claim codes, or edit the catalog. This is the root loophole; most others derive from it.
Fix: enable RLS with per-user policies; all agency writes go through authenticated server endpoints. One sprint of work.
#2 · Client-side enforcement (cooldown, duplicate block, eligibility gate, auto-approval)
The rejection cooldown, the already-applied block, the eligibility gate, and the auto-approve decision are all JavaScript — bypassable via console or crafted URLs. The checks are real (real rules, real documents, real biometrics) but the decision point is in the browser.
Fix: a thin rules service evaluates and decides server-side; the client only displays.
#3 · Claim codes stored in plaintext
The 2FA pick-up code sits readable in the applications row; anyone with the key could read it and claim without the SIM.
Fix: hash server-side, verify server-side, rate-limit attempts.
#4 · Captured-document state lives in localStorage
Clearing the browser "un-verifies" documents; only the submission snapshot (with SHA-256 hashes) freezes evidence server-side. Between capture and submission, state is browser-local.
Fix: a server-side document store keyed to the user, with retention rules.
#5 · OCR legitimacy is heuristic, not cryptographic
Type matching is keyword-based; identity matching is token overlap with the SSO name; freshness parses OCR'd dates; the duplicate check catches only bit-identical images (re-photographing defeats it). "Use Anyway" exists as a labeled demo bypass.
Fix: issuer verification — registry lookups (PSA/SSS/barangay e-certs) and signed QR documents. Image analysis alone can never prove authenticity; that's the design position.
#6 · Liveness threshold checked client-side
The result endpoint is documented as backend-to-backend; we call it from the browser and enforce ≥95 there — a tampered client could skip it. The scan itself cannot be faked (it's eGov's hosted scanner), only our reaction to the score.
Fix: backend fetches the result and gates the submission.
#7 · API secrets in client JS, in a public repo
SSO partner secret, eMessage token, liveness key, AI access code — all visible. Accepted consciously for the sandbox; all keys rotate after the event.
Fix: backend proxy / edge functions hold every secret.
#8 · The double-submission race (found and fixed — tell this story)
Scanner completion fired via both postMessage and our 3-second poll; two in-flight result checks each inserted an application → duplicate rows. Diagnosed from a user report, fixed with a resolve-once flag, an in-flight lock, and an idempotency check (skip insert if an active application exists).
Production hardening: DB unique partial index on (user, program) where status is active.
#9 · Catalog duplicated per user
Every user owns a copy of all program rows (a shortcut that let seeded per-user eligibility exist before the rules engine did). Editing a program means updating N rows; we do it with name-matched bulk updates.
Fix: single shared catalog table; per-user state computed at read time — the rules engine already makes the per-user copies redundant.
#10 · Sessions never expire; demo conveniences exist
localStorage session with no TTL; Demo Mode login; demo reset button; SMS force-route override; labeled "Continue in Demo Mode / Verify Anyway" fallbacks when sandbox APIs are down. All are visible, labeled, and none silently fake success.
Fix: eGov-managed sessions per the partner checklist; strip demo affordances at pilot.

3. Notable workarounds (engineering stories worth telling)

  • Liveness embedding: the hosted scanner is iframed with the post action instead of the redirect flow — we verified their page sends no X-Frame-Options — so verification never leaves the app shell.
  • Capture cropping: OCR quality jumped when we started cropping the camera frame to the guide rectangle (object-fit cover math) — the extractor stopped "reading" wall clocks and watermarks.
  • OCR noise filter: the extractor returns guesses ("Possible Name", "Partial Phrase", screen time); we parse its HTML into fields and drop noise keys before display and matching.
  • Token lifecycle: the AI token lives 48h with 200 credits — cached, refreshed 5 minutes early, single retry on 401, so it cannot die mid-demo.
  • Un-migrated-DB resilience: SSO writes retry without the newer socio-economic columns, so login never breaks against an older schema.
  • Cache-proof dev server: serve.py sends no-store headers after browser caching repeatedly disguised real fixes as failures.
  • API-outage resilience: we shipped through a real eMessage account ban and an eGov AI outage — every path fails soft with labeled fallbacks and auto-resumes when service returns.
